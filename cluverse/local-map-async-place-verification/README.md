# 로컬맵 외부 장소 검증과 트랜잭션 분리

게시글에 첨부한 장소를 외부 지역 검색 API로 다시 검증하는 동안 DB 트랜잭션과 커넥션을 점유하던 구조를 개선한 사례입니다. 핵심 게시글을 먼저 커밋하고 장소 검증과 연결을 별도의 실패·커밋 경계로 분리했습니다.

전체 Cluverse 서버에서 게시글·장소 저장 경계를 비교하는 Service, Processor, 이벤트 핸들러, 장소 Upsert와 핵심 계약 테스트만 선별하고 기존 사례의 패키지·의존 방향으로 정리했습니다.

## 관련 글

- [Cluverse #8: 로컬맵 개발 - 외부 API 대기를 게시글 저장에서 분리하기](https://velog.io/@bebeis/Cluverse-8-local-map)

## 문제

- 외부 장소 재검색을 게시글 저장 트랜잭션 안에서 기다려 API 지연이 응답과 DB 커넥션 점유 시간에 그대로 더해졌습니다.
- Hikari 풀 5개와 외부 지연 300ms 조건에서 외부 대기만으로 이론적 상한이 약 16.7 req/s로 제한됐습니다.
- 장소 검증 timeout이 발생하면 본문과 메타 저장까지 함께 롤백됐습니다.
- 게시글과 장소 연결은 실패했을 때 남아야 하는 결과가 다르지만 하나의 생명주기로 취급했습니다.

## 해결

1. 첫 번째 트랜잭션은 Post와 PostMeta 저장만 책임집니다.
2. 장소가 있으면 게시글 ID와 선택 장소를 이벤트로 발행합니다.
3. `AFTER_COMMIT` 리스너만 이벤트를 받아 롤백된 게시글의 장소 검증을 차단합니다.
4. 외부 provider 호출은 전용 executor에서 트랜잭션 없이 실행합니다.
5. 검증된 장소만 별도의 짧은 트랜잭션으로 Upsert하고 PostPlace를 연결합니다.
6. 장소 검증·연결 실패 시 게시글은 유지하고 장소 연결만 남기지 않습니다.
7. `requestId`로 응답 유실 뒤 재시도를 기존 게시글 하나로 수렴시킵니다.

## 실패 결과

| 실패 지점 | 남는 결과 |
| --- | --- |
| 게시글 저장 롤백 | 게시글 없음, 장소 검증 미실행 |
| 외부 장소 검증 실패·timeout | 게시글 유지, 장소 연결 없음 |
| 장소 연결 트랜잭션 실패 | 게시글 유지, 장소 연결 없음 |
| 응답 유실 뒤 동일 `requestId` 재시도 | 기존 게시글 반환 |

## 버전별 코드

- [`v1-transactional-place-verification/`](./v1-transactional-place-verification/): 외부 검증을 포함한 단일 저장 트랜잭션
- [`v2-after-commit-async-verification/`](./v2-after-commit-async-verification/): 커밋 후 비동기 검증과 별도 연결 트랜잭션

두 버전은 같은 `LocalMapPostWriteService` 진입점을 유지합니다. 게시글 유스케이스는 `cluverse.post`, 외부 장소 검증과 저장은 `cluverse.place`가 소유하며 Service는 Repository를 직접 참조하지 않습니다.

공통 게시판·회원 검증, selection token의 HMAC 구현, API 응답 래퍼, 계측기와 부하 스크립트는 생략해 독립 빌드를 보장하지 않습니다.

## 결과

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| SLO 만족 최대 지속 RPS | 15 | 103 | 6.87배 |
| 게시글 작성 평균 | 359.20ms | 28.10ms | 92.2% 감소 |
| 게시글 작성 p99 | 426.25ms | 43.98ms | 89.7% 감소 |
| DB 트랜잭션 평균 | 338.40ms | 16.41ms | 95.2% 감소 |
| DB 트랜잭션 p99 | 357.41ms | 31.26ms | 91.3% 감소 |
| Hikari active 최대 | 5 | 3 | 더 높은 부하에서도 감소 |

V2 104 RPS에서는 API p99가 49.67ms였지만 provider 호출 3,122건 중 13건이 30초 안에 도달하지 못해 최대 처리량에서 제외했습니다. API 응답뿐 아니라 비동기 작업 완료 수까지 검증한 103 RPS를 최종 결과로 사용했습니다.
