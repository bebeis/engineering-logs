# 게시판별 기준의 준실시간 인기글 승격

매일 한 번 최근 게시글을 훑고 모든 게시판에 같은 점수 기준을 적용하던 인기글 선발을 개선한 사례입니다. 좋아요·댓글이 저장된 직후 변경된 게시글 하나만 판정하고, 최근 반응 분포로 계산한 게시판별 기준을 적용해 승격 지연과 활동량 편향을 줄였습니다.

전체 Cluverse 서버에서 일일 스캔과 인라인 판정을 비교하는 Service·Implement, 점수·정책 계산, 멱등 승격과 48시간 생명주기, 핵심 계약 테스트만 선별하고 기존 사례의 패키지·의존 방향으로 리팩토링했습니다.

## 관련 글

- [Cluverse #6: 게시판별 눈높이로 승격하는 준실시간 인기글 설계](https://velog.io/@bebeis/cluverse-6-popular-post)

## 문제

- 오전 10시에 반응을 얻은 글도 다음 날 오전 1시 배치가 끝날 때까지 인기글로 노출되지 않았습니다.
- 배치 주기를 줄이면 점수가 변하지 않은 최근 48시간 게시글까지 반복해서 읽어야 했습니다.
- 모든 게시판에 같은 절대 점수를 적용해 활동량이 많은 게시판이 인기글을 독점할 수 있었습니다.
- 좋아요와 댓글이 동시에 저장되면 같은 게시글을 중복 승격할 수 있습니다.
- 승격 뒤 넓어진 노출로 증가한 반응을 그대로 다음 기준 표본에 넣으면 시스템이 만든 노출 효과가 기준을 끌어올립니다.

## 해결

1. 좋아요와 댓글이 성공적으로 저장된 뒤 해당 `postId`의 snapshot만 읽어 승격을 판정합니다.
2. 작성 후 48시간이 지났거나 삭제된 글은 판정 대상에서 제외합니다.
3. `좋아요 × 3 + 댓글 × 2`로 점수를 계산하고 게시판별 승격 기준과 비교합니다.
4. 최근 7일의 게시판별 반응 분포에서 상위 분위수 기준을 계산합니다.
5. 표본이 부족하면 기본 기준을 사용하고, 새 기준은 이전 값과 스무딩해 급격한 변화를 막습니다.
6. 정책 계산 배치는 유지하되 인기글을 직접 선발하지 않으며, 계산 결과는 MySQL과 인스턴스 메모리 캐시에 둡니다.
7. `(algorithm_version, post_id)` unique 제약과 UPSERT로 좋아요·댓글 동시 판정을 하나의 승격 결과로 수렴시킵니다.
8. 승격 실패는 이미 저장된 상호작용을 롤백하지 않고 다음 상호작용에서 다시 판정합니다.
9. 작성 후 48시간이 지나면 최종 점수를 조건부 갱신하고, 정책 표본에는 승격 전 `score_at_promotion`을 사용합니다.

## 실패 결과

| 실패 지점 | 남는 결과 |
| --- | --- |
| 좋아요·댓글 저장 실패 | 상호작용 없음, 승격 판정 미실행 |
| snapshot·정책 조회 또는 승격 실패 | 상호작용 유지, 인기글 미승격, 다음 상호작용에서 재판정 |
| 좋아요·댓글의 동시 승격 | unique UPSERT로 게시글당 승격 결과 하나 유지 |
| 한 게시판의 정책 갱신 실패 | 해당 게시판은 이전 기준 유지, 다른 게시판 갱신 계속 |
| 최종 점수 확정 중 중복 실행 | 아직 확정되지 않은 행만 조건부 갱신 |

## 버전별 코드

- [`v1-daily-global-threshold-scan/`](./v1-daily-global-threshold-scan/): 최근 48시간 게시글을 일일 스캔하고 전역 고정 기준으로 승격
- [`v2-interaction-board-threshold-promotion/`](./v2-interaction-board-threshold-promotion/): 상호작용 직후 단건 판정과 게시판별 동적 기준

두 버전은 `PopularityPromotionService`가 유스케이스 진입점을 소유하고 실제 읽기·쓰기와 계산은 `cluverse.popularity.service.implement`로 내립니다. Service는 Repository를 직접 참조하지 않으며, 좋아요·댓글 저장과 인기글 승격은 실패 결과가 다른 별도 경계로 유지합니다.

실제 JPA 엔티티·QueryDSL 조회 구현, Controller와 응답 DTO, 스케줄러 설정, Caffeine·Micrometer 구성과 부하 스크립트는 생략했습니다. 각 버전의 main 코드는 독립적으로 컴파일할 수 있지만 테스트 실행을 위한 빌드 설정과 JUnit 의존성은 포함하지 않습니다.

## 결과

AWS 테스트 환경에서 인라인 판정을 끈 기준선과 켠 조건을 각각 50 RPS로 60초씩 3회 측정했습니다. 승격 UPSERT를 제외하고 매 상호작용에서 수행되는 snapshot 조회와 판정 비용을 비교한 결과입니다.

| API | 인라인 판정 OFF p95 | 인라인 판정 ON p95 | 관측 차이 |
| --- | ---: | ---: | ---: |
| 좋아요 | 41.69ms | 47.75ms | +6.07ms |
| 댓글 | 57.28ms | 61.06ms | +3.78ms |

총 3,606건에서 실패와 dropped iteration은 없었습니다. snapshot 조회는 `post_id` 기준 `actual rows=1`, `loops=1`이었고, 측정 중 Hikari pending 최댓값은 0, MySQL CPU 최댓값은 약 5.08%였습니다. 현재 지연 예산에서는 동기 판정을 유지하고, 실제 초과가 관측될 때 비동기화를 검토합니다.
