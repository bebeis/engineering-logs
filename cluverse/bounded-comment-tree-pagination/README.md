# n-depth 댓글의 요청 비용 제한과 경로 조회

루트 댓글 수만 제한한 뒤 각 루트의 모든 자손을 붙이던 API를 개선한 사례입니다. 기본 목록을 부모별 직계 자식 커서로 제한하고 깊은 문맥은 별도 스레드 조회로 분리해, 트리 모양과 관계없이 한 요청이 반환할 범위를 먼저 정의했습니다.

전체 Cluverse 서버에서 댓글 페이지 계약, 복합 커서, 재귀 CTE와 영구 path 비교, 답글 작성·삭제 잠금과 핵심 계약 테스트만 선별하고 기존 사례의 패키지·의존 방향으로 리팩토링했습니다.

## 관련 글

- [Cluverse #7: n-depth 댓글을 제한된 비용으로 조회하기](https://velog.io/@bebeis/Cluverse-7-comment-path-enumeration)

## 문제

- 루트 댓글 `limit=20`만 지켜도 루트 하나에 답글 5만 개가 달리면 응답은 수만 건까지 커질 수 있었습니다.
- 최대 depth 5는 깊이만 제한하며, 한 부모 아래의 분기 수에는 상한을 만들지 못합니다.
- 여러 가지를 순회하다 멈춘 전체 트리는 단일 커서로 재개 지점을 표현하기 어려워 누락·중복 위험이 있습니다.
- 재귀 CTE 결과의 최종 `LIMIT`은 응답 행을 줄여도 DB가 이미 방문·정렬한 행 수까지 제한한다고 보장하지 않습니다.
- 자식 존재 확인 뒤 leaf를 삭제하는 사이 답글이 추가되면 사라진 부모를 가리키는 경쟁 조건이 생깁니다.

## 해결

1. 댓글 관계는 쓰기가 단순한 `parent_id` 인접 리스트로 유지하고 작성 depth만 5로 제한합니다.
2. 기본 목록은 한 부모의 직계 자식을 `(created_at, comment_id)` 복합 커서로 `limit + 1`개만 읽습니다.
3. 최초 페이지의 `asOf`와 `snapshotMaxCommentId`를 커서에 유지해 이후 추가된 댓글이 같은 페이지 집합에 섞이지 않게 합니다.
4. 여러 depth가 필요한 문맥은 시작 댓글 하나를 갖는 스레드 API로 분리합니다.
5. 스레드 기준안은 재귀 CTE에서 `created_at + comment_id` 경로를 만들어 깊이 우선 순서를 고정합니다.
6. 영구 path는 `(post_id, path)` 인덱스 범위 조회와 댓글 쓰기·인덱스 비용을 비교하는 실험안으로 둡니다.
7. 답글 작성과 삭제가 같은 부모·대상 행을 `FOR UPDATE`로 먼저 잠그게 해 자식 확인과 INSERT·DELETE를 직렬화합니다.
8. 자식이 있는 댓글은 soft delete해 연결점을 보존하고 leaf만 물리 삭제합니다.
9. 제한된 ID를 먼저 고른 뒤 작성자·좋아요·차단 정보를 한 번에 조립하며, 삭제·블라인드 문구는 행 제거 대신 표시 단계에서 바꿉니다.

## 실패 결과

| 상황 | 결과 |
| --- | --- |
| 답글 작성이 먼저 부모 잠금 획득 | 답글 저장 후 삭제가 자식을 확인하고 soft delete |
| leaf 삭제가 먼저 대상 잠금 획득 | 부모 물리 삭제 후 답글 작성은 부모 없음으로 실패 |
| 자식이 있는 댓글 삭제 | 행과 경로 유지, 내용만 삭제 상태로 표시 |
| 페이지 도중 새 댓글 작성 | 최초 커서의 snapshot 밖이므로 다음 페이지 집합에서 제외 |
| 잘못된 커서·다른 게시글의 부모 | 조회 전에 거부 |
| 영구 path 생성 실패 | 댓글 작성 트랜잭션 전체 롤백 |

## 버전별 코드

- [`v1-root-page-full-subtree/`](./v1-root-page-full-subtree/): 루트 페이지마다 선택된 루트의 전체 자손 반환
- [`v2-sibling-cursor-recursive-thread/`](./v2-sibling-cursor-recursive-thread/): 직계 자식 복합 커서와 별도 재귀 CTE 스레드, 삭제 직렬화
- [`v3-persisted-path-thread-experiment/`](./v3-persisted-path-thread-experiment/): 영구 path와 인덱스 범위 조회 비교안

각 버전은 `CommentQueryService`가 조회 계약을 소유하고 실제 페이지 읽기는 `cluverse.comment.service.implement` 경계로 내립니다. 쓰기에서는 `CommentWriteProcessor`가 부모 잠금부터 저장·삭제까지 하나의 트랜잭션 단위로 묶는 계약을 표현하며 Service는 Repository를 직접 참조하지 않습니다.

실제 JDBC RowMapper·화면 Projection, 회원·차단·반응 조인, Controller, 예외 응답, JPA 트랜잭션 설정과 측정 스크립트는 생략했습니다. 각 버전 main 코드는 독립적으로 컴파일할 수 있지만 테스트 빌드 설정과 JUnit 의존성은 포함하지 않습니다.

## 결과

- 기본 목록은 서브트리 전체 크기와 무관하게 반환 `limit`, ID 조회 `limit + 1`로 제한됩니다.
- 동일한 생성 시각의 댓글도 `comment_id`를 tie-breaker로 사용해 순서를 고정합니다.
- 재귀 CTE와 영구 path는 결과 동등성, 깊은 페이지의 방문 행 수, 임시 테이블·filesort, DB CPU뿐 아니라 댓글 쓰기 지연과 인덱스 크기까지 함께 비교해야 합니다.
- 글 작성 시점에는 이 성능 측정이 완료되지 않았으므로 영구 path가 더 낫다는 결론을 내리지 않았습니다.
